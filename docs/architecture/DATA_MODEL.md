# WYN V1.0.0 Logical Data Model

**Status:** PROPOSED — Architecture design only; no schema or migration is authorized.
**Owner:** Database Engineer
**Reviewers:** WYN CTO, Software Architect, QA & Security, DevOps / SRE
**Source of truth:** the Founder-approved V1 product specification. Where that specification leaves policy open, this document records an invariant or a Founder decision rather than inventing behavior.

## 1. Goals and database boundary

V1 uses one PostgreSQL primary database for the modular monolith. Modules own their tables logically and may change them only through the owning module's public application interface. A foreign key is not permission to read another module's private data. Cross-module reads use purpose-built query services/read models; cross-module side effects use transactional outbox events. This keeps transactions simple at launch without creating service-shaped operational complexity.

Conventions:

- IDs are opaque, globally unique, time-sortable identifiers generated by a trusted server. Public APIs never infer authorization from an ID.
- All timestamps are timezone-aware UTC. Mutable rows carry `created_at`, `updated_at`, and, where useful for optimistic concurrency, `version`.
- Enumerated states are constrained to known values. State transitions are validated by the owning module in the same transaction.
- Foreign keys normally use `RESTRICT`/`NO ACTION`. Privacy-critical history is not accidentally cascade-deleted. Explicit retention workflows perform deletion or anonymization.
- User-generated content (UGC) is safely soft-deleted; credentials, short-lived tokens, temporary uploads, and derived data use explicit expiry/purge policies.
- Normalized handles, emails, hashtags, and flag keys use deterministic normalization and unique indexes. Display text preserves the user's original value.
- Counters and ranking projections are derived, non-authoritative data. Source relations/events remain authoritative.

## 3. Identity, authentication, and profiles

### `users`

One row per Consumer account: `id`, lifecycle `status` (for example pending verification, active, restricted, suspended, banned, deletion pending), account visibility (public/private), age-eligibility assertion/result rather than unnecessary birth-date exposure, moderation timestamps, `created_at`, `updated_at`, `deleted_at`, `version`. Status and deletion fields are server-controlled. Index status and `(status, created_at)` for operational scans. A user soft deletion revokes sessions immediately and hides owned content through authorization filters; physical erasure/anonymization follows the Founder-approved retention/legal policy.

### `identities`

Authentication identity owned by exactly one user: `id`, `user_id`, `provider` (`EMAIL` initially; reserved identifiers allow future Google/Apple), normalized provider subject, normalized email where applicable, verification state/timestamp, password credential reference/hash only for the local provider, and timestamps. Enforce unique `(provider, provider_subject_normalized)` and, under the approved email-account-linking policy, a partial unique normalized-email index. A user may own several identities, but each identity has one owner. Passwords are stored only as approved salted password hashes; raw passwords and provider tokens are never stored here.

### `sessions` and one-time credentials

`sessions` belongs to one user and stores only an opaque-token digest, session family/device label, issued/last-seen/absolute-expiry timestamps, revocation timestamp/reason, and risk metadata minimized to operational need. Unique token digest; indexes `(user_id, revoked_at, expires_at)` and `expires_at` for revocation/purge. Session rotation/revocation uses row locking or compare-and-swap on `version`. Consumer sessions are structurally and cryptographically separate from Admin sessions.

Email-verification and password-reset credentials live in dedicated relations containing a one-way token digest, `user_id`/`identity_id`, purpose, expiry, consumed/revoked timestamps, and attempt metadata. A conditional uniqueness rule permits only the intended number of active credentials per purpose. Consumption is an atomic `UPDATE ... WHERE consumed_at IS NULL AND expires_at > now()`.

### `profiles`

Exactly one profile per user (`user_id` primary/foreign key): normalized unique username, display name, bio, validated website URL, avatar/cover `media_asset_id`, privacy preferences including Likes-tab and graph visibility once approved, and timestamps. Username uniqueness is case/Unicode-normalized. Search uses a trigram index on normalized username/display name; external website data is always untrusted. Username history/reservation policy remains **FD-02**.

## 4. Social graph and privacy edges

- `follows(follower_user_id, followed_user_id, created_at)`: composite primary key; check actors differ; indexes in both directions. It represents only an accepted active relation.
- `follow_requests(id, requester_user_id, target_user_id, status, decided_at, created_at, version)`: actors differ; one partial unique pending request per ordered pair; index target/status/time and requester/status/time. Accept locks the request and relevant user/privacy rows, rechecks block and account state, creates the follow idempotently, then transitions the request in one transaction.
- `blocks(blocker_user_id, blocked_user_id, created_at)`: composite primary key and actors-differ check; reverse-pair index supports symmetric visibility enforcement. Creating a block atomically removes both-direction follows and pending requests according to policy. A block is a mandatory authorization predicate, including fetches by direct ID.
- `mutes(muter_user_id, muted_user_id, created_at)`: composite primary key and actors-differ check. Mute is directional filtering, not authorization, and is not revealed to the muted user.

Every graph query is bounded and cursor-paginated. The unresolved same-Club block behavior is **FD-11**; until approved, design and tests use the privacy-preserving deny-by-default branch rather than silently exposing content.

## 5. Drops, media, topics, mentions, and polls

### `drops`

`drops(id, author_user_id, kind, body, visibility, lifecycle_status, quoted_drop_id?, public_distribution_of_drop_id?, created_at, published_at?, edited_at, deleted_at, version)`. `published_at` is server-controlled: it is set once, in the atomic transition from draft to published, and is immutable thereafter. A published Drop may be edited only when `server_now < published_at + interval '30 minutes'`; the trusted edit transaction locks the row and evaluates that predicate against database/server time, never client time, `created_at`, or `edited_at`. `kind` distinguishes original/quote behavior without overloading a client flag. Self-consistency checks reject an ID quoting itself; application invariants prevent quote cycles. Index `(author_user_id, created_at, id)` with a live-row predicate, `(visibility, created_at, id)` for public candidates, quoted target, and moderation/lifecycle status. Body search receives a PostgreSQL full-text GIN index only for visible eligible text. Soft deletion clears it from all surfaces while retaining the minimum record required by moderation/retention policy.

### Media and the authoritative nine-image invariant

`media_assets` is owned by Media and records owner, purpose, quarantine/permanent object key references (never public trust tokens), detected type, bytes, decoded dimensions/pixel count, checksum, processing status, safe variants metadata, timestamps, expiry, and version. `upload_intents` binds a short-lived upload to owner, purpose, maximum bytes/type, idempotency key, expiry, and consumed state. Only `READY` assets belonging to the acting user and authorized purpose may attach.

`drop_media(drop_id, media_asset_id, position, attached_at)` uses zero-based positions and has a composite primary key `(drop_id, media_asset_id)`, unique `(drop_id, position)`, `CHECK position BETWEEN 0 AND 8`, and unique media attachment according to the approved reuse policy. **A trusted create/edit transaction locks the Drop, rechecks ownership/status and READY assets, writes the complete attachment set, and rejects a count above nine. The future schema must also add a database constraint trigger/deferred invariant that rejects more than nine rows per Drop.** The position check alone is insufficient because sparse or duplicate-attempt patterns must not bypass the count. Request idempotency and the uniqueness constraints make retries safe.

### Topics and references

- `hashtags(id, normalized_tag, display_tag, created_at)`: unique normalized tag; trigram search index.
- `drop_hashtags(drop_id, hashtag_id)`: composite primary key and reverse index for topic feeds. Tags are parsed and validated server-side in the Drop transaction.
- `mentions(id, source_type, source_id, mentioned_user_id, byte/text range or normalized token, created_at)`: target and source indexes; a constrained target/source type model prevents arbitrary polymorphic values. Notifications are derived only after visibility and block checks.
- Poll relations (required by the approved Drop/Club Drop scope): `polls(drop_id, closes_at, result_visibility, version)`, ordered `poll_options`, and unique voter selection records. Exact choices, duration, vote-change and anonymity rules remain **FD-05**; no physical design is frozen before that decision.

## 6. Engagement, comments, and scoped signals

### Source relations

- `likes(user_id, drop_id, created_at)`, `saves(user_id, drop_id, created_at)`: composite primary keys and reverse time indexes. Save rows are private to their owner.
- `comments(id, drop_id, author_user_id, parent_comment_id?, root_comment_id?, body, status, created_at, edited_at, deleted_at, version)`: parent must belong to the same Drop; maximum nesting is an application/domain constraint; indexes `(drop_id, created_at, id)`, parent, author, and live status. Soft-delete preserves thread shape with content hidden.
- `redrops(id, user_id, source_drop_id, quote_drop_id?, distribution_scope, created_at, deleted_at)`: one active plain redrop per user/source/scope where product semantics require it; quote redrops point to their own Drop. Source, actor, and time indexes support feeds and undo.
- `views(id, viewer_user_id?, privacy-safe viewer/session dedupe key?, drop_id, distribution_id, occurred_at, validity_status)`: append-oriented and partition-ready. The exact view definition/deduplication window remains **FD-04**; clients never submit authoritative counts.

All engagement writes recheck actor status, target visibility, block relationship, moderation state, and Club access in the same transaction. Unique source constraints make like/save/redrop retries idempotent. Derived counts update asynchronously or through guarded deltas and are repairable from source facts.

### Scoped engagement and ranking isolation

`engagement_events` is the trusted append-only ranking input/projection source:

- `id`, immutable `source_event_id` (unique), actor, target type/id, action type, `occurred_at`;
- `scope_type`: `GLOBAL_PUBLIC` or `CLUB`;
- `scope_id`: null only for `GLOBAL_PUBLIC`, otherwise the Club ID;
- `distribution_id` and optional `public_origin_distribution_id`;
- eligibility/invalidated state and policy/ruleset version; no client-authored score.

A Club Drop has only `CLUB(club_id)` engagement at its Club distribution. Those events can feed Club Popular/Trending only. Sharing or ReDropping eligible content into a public surface creates a **new public distribution row/event**; only engagement occurring against that public distribution may create `GLOBAL_PUBLIC` events. It never copies, converts, or aggregates the source Club engagement. Enforce `CHECK ((scope_type='GLOBAL_PUBLIC' AND scope_id IS NULL) OR (scope_type='CLUB' AND scope_id IS NOT NULL))`, unique `source_event_id`, and indexes `(scope_type, scope_id, occurred_at)`, `(target_type, target_id, scope_type, occurred_at)`, and distribution/time. Ranking projections are keyed by scope and ruleset so a query cannot accidentally mix Club and Global datasets.

## 7. Clubs

- `clubs(id, owner_user_id, slug, name, description, rules, visibility, status, avatar/cover_media_id, created_at, deleted_at, version)`: unique normalized slug; search indexes over eligible name/description; owner must have an active OWNER membership.
- `club_roles(id, club_id, name, rank, system_role, created_at)`: unique `(club_id, name)` and `(club_id, rank)`. V1 role names are Owner, Admin, Moderator, Member, while permissions are separate granular role-permission assignments. Exact matrix is **FD-08**.
- `club_members(club_id, user_id, role_id, status, joined_at, version)`: composite primary key; indexes user/status and club/role/status. Role must belong to the same Club, enforced by a composite key/foreign key in physical design. The single active owner invariant uses a partial unique ownership marker plus a locked ownership-transfer transaction; Owner cannot leave without an approved transfer.
- `club_join_requests(id, club_id, requester_user_id, status, decided_by_user_id?, reason?, created_at, decided_at, version)`: one pending request per Club/user; target queue and requester indexes. Decision locks request and rechecks the actor's granular permission.
- `club_posts(club_id, drop_id, author_membership reference, status, pinned_at?, pinned_by_user_id?, created_at)`: one scope row per Club Drop, unique `drop_id` in V1; indexes Club/status/pinned/time and Drop. A composite membership reference proves membership at creation while authorization still rechecks current state. Pin/unpin and moderation create audit events. This explicit relation is preferred over treating `drops.club_id` as an incidental filter.

Private Club rows/content never enter public search/read models, previews, notifications, CDN authorization, or direct-ID responses. Club creation/join policy remains **FD-09**.

## 8. Basic 1:1 chat

- `conversations(id, kind='DIRECT', direct_pair_key, status, created_at, updated_at, version)`: one canonical unordered user-pair key prevents duplicate 1:1 conversations.
- `conversation_members(conversation_id, user_id, state, joined_at, last_read_message_id?, last_read_at?, deleted_for_user_at?)`: composite primary key; exactly two distinct members for a direct conversation is enforced by a locked creation transaction and future deferred database invariant. User/inbox-time index supports bounded inbox reads.
- `message_requests(id, conversation_id, sender_user_id, recipient_user_id, status, created_at, decided_at, version)`: one pending request per conversation/recipient. Acceptance/decline is compare-and-swap and rechecks blocks.
- `messages(id, conversation_id, sender_user_id, message_type, text_body?, media_asset_id?, reply_to_message_id?, shared_entity_type?, shared_entity_id?, created_at, sender_deleted_at?, moderation_hold_at?, version)`: type-specific check constraints require exactly the allowed payload. Sender must be a member; replies must belong to the same conversation. Index `(conversation_id, created_at, id)`, sender/time, reply target, and moderation hold.

The durable message transaction authorizes participation/request/block state, inserts the message, updates conversation activity, and emits an outbox event. Realtime is never authoritative. Send, read/fetch, request, and delivery each re-evaluate permission/block/visibility. Sender deletion hides the message under Founder-approved semantics (**FD-10**) but cannot destroy evidence retained for an active report; private message body is excluded from general logs/search/analytics.

## 9. Notifications

`notifications(id, recipient_user_id, type, actor_user_id?, target_type?, target_id?, group_key?, source_event_id, created_at, read_at, invalidated_at, payload_version)` has unique `(recipient_user_id, source_event_id)` (or approved grouping key/window), an unread partial index, and `(recipient_user_id, created_at, id)`. Payload contains identifiers/minimal display metadata, not a permanent copy of private content; read APIs recheck target visibility and return unavailable when access changed.

`notification_preferences(user_id, notification_type, in_app_enabled, future_channel settings, updated_at, version)` has a composite primary key. Mandatory System notification behavior is a policy constraint. Notification workers recheck preference, block, privacy, account/entity state and deduplication immediately before insert/delivery.

## 10. Reports, moderation, appeals, and immutable audit

- `reports(id, reporter_user_id, target_type, target_id, reason_code, context, status, created_at)`: constrained target types User/Drop/Comment/Club/Message; reporter/target/status indexes; restricted access. Evidence references are captured minimally and independently retained so safe deletion does not erase an active case. Consumer responses never reveal reporter identity.
- `moderation_cases(id, status, priority, assigned_admin_principal_id?, opened_at, resolved_at?, version)`, with `case_reports(case_id, report_id)` allowing deduplicated review without merging evidence destructively.
- `moderation_actions(id, case_id, actor_admin_principal_id, action_type, target_type/id, reason, policy_version, effective_at, expires_at?, outcome, created_at, supersedes_action_id?)`: append-only. Types cover no action, warning, remove, restrict, suspend and ban. Corrections append superseding records; ordinary Admin roles cannot update/delete history.
- `appeals(id, case_id, appellant_user_id, status, reason, created_at, decided_at?, decided_by_admin_principal_id?, decision_reason?, version)`: eligibility/cardinality/SLA remain **FD-13**; unique active appeal as eventually approved.
- `audit_logs(id, occurred_at, actor_type/id, session_id?, action, target_type/id, reason?, request_id, correlation_id, before_digest?, after_digest?, outcome, metadata)`: append-only, least-privilege readable, time/actor/target/action/request indexes, and partition-ready. Database privileges deny application update/delete; integrity chaining/WORM export may be added according to the Founder-approved retention and threat model. Never store secrets, tokens, passwords, unnecessary PII, or private message bodies.

Moderation action and audit append happen atomically with the authoritative state change and outbox event. Retention, evidence access, notices, appeal policy, and admin audit retention remain **FD-13/FD-14**.

## 11. Admin authorization and feature flags

Admin identities, sessions, and authorization grants use separate relations and token namespace from Consumer authentication. Logical relations are `admin_principals`, `admin_identities`, `admin_sessions`, `admin_roles` (OWNER, SUPER_ADMIN, MODERATOR, SUPPORT, ANALYST, CONTENT_ADMIN), `admin_permissions`, role-permission mappings, and principal-role grants. Every grant has grantor, scope, effective/expiry/revocation fields. Permissions are action/resource based; no query relies on `role == admin`. Sensitive actions require a recent step-up marker, permission, reason, and immutable audit row. Exact permission matrix and retention are **FD-14**.

`feature_flags(id, key, description, enabled_state, rollout_config, environment, version, updated_by_admin_principal_id, updated_at)` has unique `(environment, key)` and JSON/config validation against a server-owned schema. `feature_flag_changes` is append-only. `clubs_enabled`, `chat_enabled`, `trending_enabled`, and `top100_enabled` are initial candidate keys, not authorization controls; disabled/enabled code paths still enforce normal policy.

## 12. Transactional outbox and projections

`outbox_events(id, aggregate_type, aggregate_id, aggregate_version, event_type, schema_version, payload, occurred_at, available_at, dispatched_at?, dispatch_attempt_count, dispatch_locked_until?, dispatch_error_code?, correlation_id)` is inserted in the same transaction as its source fact. Unique `(aggregate_type, aggregate_id, aggregate_version, event_type)` or an explicit idempotency key prevents duplicate logical events. A dispatcher claims the `(available_at, occurred_at)` queue where `dispatched_at IS NULL`, reads a versioned registry of required consumers by event type, and in one transaction materializes one `outbox_deliveries(event_id, consumer, available_at, delivered_at?, attempt_count, locked_until?, last_error_code?)` row for **every** required consumer before setting `outbox_events.dispatched_at`. The delivery relation has primary key `(event_id, consumer)` and an available-delivery partial index on `(available_at, event_id)` where `delivered_at IS NULL`; aggregate history is indexed by `(aggregate_type, aggregate_id, aggregate_version)`. A dispatcher crash rolls back both the jobs and marker, and uniqueness makes a retry safe. Adding a consumer requires an explicit replay/backfill decision for earlier events.

Each consumer worker claims only its bounded delivery rows with row locking/skip-locked semantics, uses `(consumer, event_id)` as the idempotency key, and sets that delivery's `delivered_at` only after its projection transaction succeeds. Retries use backoff and move a poison **delivery** to a reviewable dead-letter record without hiding the event from other consumers. `event_consumer_receipts(consumer, event_id, processed_at, result)` has a composite primary key and is written atomically with the consumer effect; it prevents duplicate handling after a lease expiry. Search documents, feed candidates, counters, notification grouping, Trending and Top 100 tables are rebuildable projections with `last_event_id`/ruleset version and must apply visibility checks at read time.

## 13. Integrity and concurrency rules

1. **Authorization precedes and accompanies writes.** Lock/re-read the resource and privacy edges in the mutation transaction; stale client state is never sufficient.
2. **Idempotency is persisted.** Risky create endpoints map `(principal, route/action, idempotency_key)` to request hash and outcome with expiry. A key reused with a different hash is rejected.
3. **Uniqueness wins races.** Follow, pending request, like, save, membership, conversation-pair, media position, and outbox constraints are the final race defense; application prechecks improve errors only.
4. **Optimistic concurrency protects edits.** Mutations compare `version`; state machines and ownership transfer additionally lock rows in a documented order to avoid deadlocks.
5. **No lost counters.** Counters use atomic guarded updates or async aggregation, never read-modify-write from client values. Reconciliation jobs compare them to sources.
6. **Deletion and enforcement propagate.** A deletion/moderation/privacy transaction changes the authoritative state and emits an outbox event. All reads still filter authoritative state during projection lag.
7. **Nine images is transactional.** Create/edit serializes on the Drop, validates the final complete set, and is backed by the database-level deferred count invariant described above.

## 14. Indexing and query discipline

- Every foreign key used for authorization or cleanup has a supporting index; composite indexes follow equality predicates, then cursor sort columns `(created_at, id)`.
- Use partial indexes for live/pending/unread/undelivered rows to keep hot indexes small. Never use `OFFSET` for unbounded product lists.
- PostgreSQL full-text GIN supports eligible Drop/topic/Club text; `pg_trgm` GIN/GiST supports normalized username, display name, hashtag and Club-name tolerance. Search queries first apply visibility, block, status, and membership predicates.
- At 1k DAU, avoid premature table partitioning. Candidate first partitions at measured growth are high-volume `views`, `engagement_events`, `audit_logs`, and `outbox_events`, based on size/maintenance latency—not DAU alone.
- Query plans for feeds, inboxes, moderation queues, graph lists and searches require representative staging review. Add indexes from measured plans; do not index every column.

## 15. Soft deletion, retention, and privacy boundaries

| Data class | Logical treatment |
|---|---|
| Drops, comments, Club posts/profile UGC | `deleted_at`/status; excluded by default scopes; minimal content retained only under approved policy |
| Users | lifecycle state then anonymization/erasure workflow; immediate session revocation and surface removal |
| Messages | sender-visible deletion marker; evidence preservation only where policy/report requires |
| Likes, saves, follows, requests | generally hard-delete/terminal-state as policy permits; audit only sensitive transitions |
| Auth/reset tokens, upload intents, quarantine files | digest-only where applicable; short expiry and deterministic purge |
| Reports/cases/actions/appeals/audit | restricted retention; append-only actions/audit; deletion/anonymization only through approved legal policy |
| Outbox and projections | operational retention; archive/purge after all consumers and replay requirements are satisfied |

Database roles follow least privilege: API, worker, migration operator, read-only analytics, and privileged break-glass access are distinct. Analytics/search receive minimized eligible projections, not unrestricted base-table access. Object keys are private; signed delivery is authorized separately. Backups inherit production sensitivity and encryption/access/retention controls. Production data is not copied into development/test without explicit approval and effective anonymization.

## 17. Database Engineer review findings

- **HIGH — unresolved policy-to-constraint mapping:** FD-04/05/08/10/11/13/14 prevent final unique/check/retention constraints. Preserve them as explicit gates; do not encode assumptions in migrations.
- **HIGH — privacy joins are cross-cutting:** block, account visibility, Club membership and moderation state must be centralized in server-side policy/query interfaces and negatively tested; ad hoc joins will create IDOR/privacy leaks.
- **HIGH — retained evidence versus deletion:** message/content deletion, reports, appeals and legal retention need a Founder-approved minimization matrix before physical design.
- **HIGH — ranking contamination:** source events and every derived table must carry mandatory scope/distribution keys; null/default scope must never silently mean Global.
- **MEDIUM — hot append tables:** views, engagement, audit and outbox will grow first. Bounded retention, queue indexes and measured partition triggers are required, but partitioning at launch is not.
- **MEDIUM — polymorphic references:** mentions, shares, reports and audit targets need constrained type registries plus application/database integrity checks; arbitrary type/ID pairs are prohibited.
- **MEDIUM — multi-row invariants:** maximum nine media, two direct-chat members and one Club owner require serialized transactions plus database constraint triggers/ownership uniqueness, not client checks.
- **Review result:** logical integrity is acceptable for **PROPOSED** architecture subject to the listed Founder decisions, CTO/QA review, and a later physical-schema review. No migration or application implementation is approved by this document.
